## Actual containment and independent validation

Every consumer/generator runs with Linux **hard and soft RLIMIT_AS = 536,870,912
bytes (512 MiB)**, not merely a requested library quota. Each Rust worker checks
both active limits in `/proc/self/limits` before opening a source. An independent
child successfully allocates 16 MiB and receives `MemoryError` for an allocation
larger than the cap. The core root quota remains **268,435,456 bytes (256 MiB)**.
All workers are serial and do not fork or map files. For these workloads an
address-space ceiling also bounds resident user memory; it does not contain an
arbitrary descendant process tree or kernel filesystem cache.

`wait4` records per-child peak RSS and user/system CPU. `/proc` samples record
post-exec RSS/VM/FD peaks and last available kernel I/O counters. `wait4` peak RSS
can include the Python fork/pre-exec footprint; it is reported alongside sampled
post-exec peaks. Sampling is every 50 ms and may miss brief peaks; wait4 remains
mandatory. Worker checks/negative allocation control establish containment.

The development generator writes real documented v7 sections and strictly ordered
keys using fixed buffers. Files have no sparse padding. Counts are within v7's
signed count limits; 64-bit offsets cross 2 GiB. Record rows carry **20 original
keys and five distinct deterministic ordinary numeric bit patterns**, seed
**0x1640 (5696)**. Metadata files contain no physical symbol records and unique
**63-byte labels**, independently exercising dictionary size. Python recipes,
Rust field checks and pinned native reads agree on the small generated inputs;
full native record scans also agree on the largest ordered digest. Expected
values come from recipes rather than a Rust-to-Rust round trip.

## Slice, limit, first-batch and I/O evidence

For the 20-million-row input, full, leading and non-leading scans each read
**2,520,033,217 source bytes**, make available **2,520,033,077 decoded-buffer bytes**
in **76,908 successful fills**, and decode **20,000,000 rows**. The leading slice
returns **2,048** rows and the non-leading slice **58,596**; their complete field
and ordered digests match independent expectations. Selection precedes projection
and accepted limits. No data pruning/index benefit is claimed from fewer outputs.

Fresh-process first full batches read **98,580 source bytes**, with measured
worker latencies **0.148–0.491 ms** in the three full runs. `head(13)` decodes exactly
13 rows, reads **65,812 source bytes**, and returns the expected complete digest;
`head(0)` decodes none (normal header/catalog/count validation still reads metadata).
Cold means empty library cache/no index. Trial zero follows fsync and advisory
POSIX_FADV_DONTNEED; it is not proof of cold physical storage. Later repeats reuse
OS cache. External process wall timing includes up to 50 ms polling overhead;
worker-internal first-batch time avoids that artifact.

Decoded-buffer counters include read-ahead/repeated metadata traversals; they are
not bytes consumed exclusively as record fields. Complete positioned-read counters
are library observations. Last sampled `/proc/io` physical-read counters are partial
snapshots and may be zero with OS cache hits; they are not substituted for complete
source work or advertised as cold-device throughput.

## Throughput result and required investigation

All timings below follow count/field/digest validation, same file and cap, serial
execution, release builds and the reported cache policy. Hardware is an AMD EPYC
9V74 VM with **five visible CPUs**, Linux **6.18.55 x86_64**, glibc **2.41**. Rust/Cargo
**1.99.1**; native compiler **GCC 14.2.0**, pinned GDX
`9e2a8c8932412010cd7d2f94727d1740143bf3da` and bundled zlib
`da607da739fa6047df13e66a2af6b8bec7c2a498`.

| Largest full scan, three trials | Median wall | Range | Standard deviation | Median user CPU |
| --- | ---: | ---: | ---: | ---: |
| Rust, 20 million wide rows | **6.827 s** | 6.825–7.130 s | 0.176 s | 6.593 s |
| Native, identical rows/fields/digest | **4.452 s** | 4.350–4.702 s | 0.181 s | 4.298 s |
| Rust, 36 million labels | **4.801 s** | 4.749–4.850 s | 0.051 s | 4.545 s |

Rust's wide-row full read takes **1.53× native wall time** here. This crosses the
plan's >10% investigation threshold; native throughput parity is **not established**.
The workload is synthetic, not a portable performance guarantee. Source bytes/work
are equal across record slices, and CPU dominates full-scan time. The retained
native M0 principal-corpus baseline is separately revalidated, not replaced by this
new workload.

The follow-up `scale_profile.py` run validates all 20 million rows/digest in three
more capped trials and times batch calls without changing the core. Median decode
and batch-fill time is **6.165 s** of **6.969 s** total; roughly **88%** of instrumented
wall time sits inside decoder/selection/batch materialization/source checks, with
about 12% in consumer field validation and digest work. These instrumented samples
are separate from the original benchmark. The measured gap therefore warrants
profiling the decoder/batch path; this does not identify an individual bottleneck
or justify unsafe/SIMD/parallel changes. Performance optimization remains follow-up
work, while M2's required correctness and memory gate passes.

A follow-up native open/UEL scan of the largest dictionary under the **same** cap
exits **1** with `std::bad_alloc`. It supplies no native metadata throughput sample.
The original scale report says this comparison was unattempted at that point;
the machine record separately retains this subsequent failed comparison. Small
native metadata validation passed. No uncapped native run or fictitious comparison
is reported.

## Author review, corrections and limitations

Author review checked ratio assertions, independent counts/ordered digests,
source/hash binding, bounded generation/sinks, actual hard-limit verification,
negative control, wait4 lifecycle, output/error propagation, split temporary quota
headroom, handle/scratch cleanup, fixed-budget growth, feature coverage and timing
comparability. Stage timing keeps the validating sink intact and fails closed if
its source shape changes. This is **author review**, not an invented independent
release review.

An initial smoke compilation used an incorrect native UEL accessor; corrected to
the pinned `gdxUMUelGet` before passing smoke/full runs. A first full attempt at
`2e14a7b` completed record cases but failed on PermissionDenied while sampling an
exiting metadata child. Its report remains **failed**. The corrected harness counts
optional /proc sampling denials, while mandatory wait4/limits/result validation
remain enforced; the successful full run observed no such denials. Review also
corrected the initially insufficient temporary-space setup from 10 to 18 GiB:
36 million 73-byte UEL run frames need about 5.256 GB of live input+output in the
final merge, fitting a 6 GiB share. The memory caps, growth thresholds, expected
results and task acceptance criteria were never relaxed.

Qualification is Linux x86_64 only. Native Windows/macOS/big-endian hardware,
>4 GiB files, oversized compressed workloads, hard physical-cache eviction,
process-tree cgroups, actual filesystem exhaustion and crash recovery remain
unrun/unclaimed. Stored/zlib correctness and bounded codec state are covered by
regression/probe tests, not by a new large-zlib throughput claim. Logical disk
quotas exclude filesystem block/inode overhead; the cap excludes kernel caches.
Fixed standard shared-owner allocator/OOM behavior, trusted scratch namespaces,
hard-link requirements and best-effort Drop cleanup remain as documented.

**M2 is complete for the qualified bounded-read scope.** The next milestone is
**M3, sorted writing**; define its numbered specifications before implementation.
Native throughput parity remains an explicit performance follow-up, not a claimed
result of this gate.
